# План: LSI-требования к SEO-текстам на основе конкурентов

Большая функциональность: интеграция Topvisor + Miratext, версионирование требований, новый UI в Настройках и переработка блока в попапе копирайтера. Реализую поэтапно, чтобы можно было проверять по частям.

## Этап 1 — Хранилище и ключи API

1. Миграция БД: 4 таблицы
   - `text_requirement_analysis` (запуски анализа: статус, hash Miratext, raw-ответы, ошибки)
   - `text_requirement_competitor` (URL конкурентов по анализу, флаги selected/excluded)
   - `text_requirement_item` (LSI-слова/фразы 2/3, приоритет, статус, is_manual)
   - `text_requirement_version` (версии: draft/active/archived, ссылка на analysis)
   Все — с GRANT для `service_role`, RLS on, доступ только через server-fn.
2. Добавляю в существующую вкладку **Настройки → API и Ключи** записи:
   - `TOPVISOR_API_KEY` + `TOPVISOR_USER_ID`
   - `MIRATEXT_API_KEY`
   Хранение через уже готовый `api_keys` (значения из БД перекрывают env).
3. Глобальные настройки LSI (project_id Topvisor, region, поисковик, глубина SERP, кол-во конкурентов, blacklist доменов, домен проекта) — храню в новой таблице `lsi_settings` (одна строка).

## Этап 2 — Backend: Topvisor + Miratext

Все server-fn в `src/lib/lsi.functions.ts` + server-only хелперы в `src/lib/lsi.server.ts` (клиенты API, парсинг, retry, rate-limit).

- `collectCompetitors({ groupId })` — тянет SERP-снимок из Topvisor (`get/snapshots_2/history` + `get/snapshots_2/competitors`), фильтрует (домен проекта, blacklist, дубли доменов, PDF/изображения), сортирует по средней позиции и покрытию ключей, выбирает N (по умолч. 3). Пишет `text_requirement_analysis` + `text_requirement_competitor`.
- `runMiratextAnalysis({ analysisId })` — отправляет `seoAnalizText` (`check_type=url`, массив URL), сохраняет hash, статус `analyzing_miratext`.
- `pollMiratextAnalysis({ analysisId })` — читает статус (`draft/working/accepted/error`), при `accepted` разбирает `tz.keywordsAll`, `repeatWordsAll`, `repeatWords2All`, `repeatWords3All`, `stats.*`, создаёт `text_requirement_item` и черновой `text_requirement_version`.
- CRUD server-fn: `listAnalyses`, `getAnalysis`, `updateCompetitor`, `updateRequirementItem`, `approveVersion`, `rollbackVersion`, `getActiveVersionForGroup`.

Ошибки понятные (нет ключа, нет SERP, <N конкурентов, лимит API и т.п.), сохраняются в `error_message`.

## Этап 3 — UI: Настройки → Требования и примеры текстов

Расширяю существующую вкладку блоком **LSI и конкуренты**:

- Верх: форма глобальных настроек (Topvisor project, регион, ПС, глубина SERP, N конкурентов, blacklist, домен проекта).
- Таблица групп: группа | URL | ключей | дата SERP | конкурентов | статус Miratext | статус требований | активная версия | обновлено | действия (Собрать / Анализ / Редактировать / Утвердить / История).
- Дровер «Редактирование требований»: список конкурентов (замена/удаление/добавление), редактор LSI-слов, фраз 2/3, рек. объём, стоп-слова, ручные требования, примеры хороших/плохих, обязательные блоки. Кнопки: Сохранить draft / Утвердить / Откатить к версии.

## Этап 4 — Попап копирайтера (SEO Texts)

- Заменяю текущий блок «Слова» на **LSI-слова и фразы** из активной версии требований группы.
- Ключевые запросы сохраняю как компактный сворачиваемый блок «Ключевые запросы».
- Новая read-only вкладка **Требования к тексту** в попапе: группа, URL, дата версии, свёрнутый список конкурентов, LSI-слова/фразы 2/3, рек. вхождения, рек. объём, обязательные блоки, примеры, стоп-слова.
- Подсветка в тексте расширяется: LSI-слова/фразы подсвечиваются, счётчики вхождений считаются по ним.
- Если активной версии нет — понятная плашка «Требования не подготовлены», редактор продолжает работать.

## Этап 5 — Отладка и приёмка

- Прогон typecheck.
- Проверка сценария: подключить ключи → собрать конкурентов по группе → запустить Miratext → отредактировать LSI → утвердить → увидеть в попапе.
- Логи raw-ответов сохраняются для отладки.

## Технические детали

- Server-fn защищены (все LSI-действия — только через backend, ключи только в env/`api_keys`).
- Retry с экспоненциальной паузой для Miratext polling, лимит попыток.
- Кэш: повторный `collectCompetitors` не запускается автоматически, только вручную или при изменении ключей группы.
- `text_requirement_item.priority` (high/medium/low) вычисляется по частоте у конкурентов + наличию в `tz.keywordsAll`.
- Активная версия — одна на группу; при `approveVersion` предыдущая переводится в `archived`.
